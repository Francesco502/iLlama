# iLlama v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a low-overhead Windows/macOS GUI launcher for `llama.cpp` that lets users select local GGUF model folders, configure common `llama-server` startup parameters, start/stop the model, chat with it, and understand startup/runtime status without using command-line flags.

**Architecture:** Use Tauri v2 as a lightweight desktop shell, React/TypeScript for the UI, and Rust for local filesystem access, settings persistence, model scanning, command construction, process management, health checks, logging, and system monitoring. The app should launch the official `llama-server` as an external sidecar or user-selected binary instead of embedding inference into the GUI process.

**Tech Stack:** Tauri v2, Rust stable, React, TypeScript, Vite, Tailwind CSS, npm, `llama-server`, GGUF metadata parsing in Rust, local JSON settings/cache files, unit tests for Rust and TypeScript, manual end-to-end validation with a small GGUF model.

---

## Product Positioning

v1 should be deliberately narrow: it is a reliable local model launcher, not a model marketplace, downloader, multi-model orchestration platform, RAG system, or plugin host. The user should be able to go from installed app to first local chat with minimal decisions:

1. Open the app.
2. Choose one or more model directories.
3. See only GGUF models found under those directories.
4. Select a model.
5. Adjust core startup parameters such as context length, CPU threads, GPU offload layers, batch size, port, and sampling defaults.
6. Start `llama-server`.
7. Read startup logs and status.
8. Chat through the local OpenAI-compatible API.
9. Stop the model and release resources.

The app should never scan the whole computer by default. Model discovery is explicit, user-directed, cached, and refreshed manually.

## v1 Scope

### Included

- User-managed model directories.
- Recursive `.gguf` scanning only inside user-selected directories.
- Lightweight GGUF metadata extraction without loading model weights.
- Model list with name, path, file size, modified time, quantization when available, architecture when available, and metadata-read status.
- Local cache keyed by absolute path, file size, and modified timestamp.
- `llama-server` binary path detection:
  - bundled sidecar path when packaged with the app;
  - user-selected binary path for development and custom installs.
- Startup parameter form with basic, performance, sampling, and advanced sections.
- Parameter presets: Low Memory, Balanced, Performance, and Custom.
- Startup command preview.
- Port availability check and optional auto-port selection.
- Start, stop, restart, and forced stop.
- Startup status: idle, starting, healthy, failed, stopping.
- Captured stdout/stderr logs with bounded in-memory retention.
- Health checks against local server endpoints.
- Chat UI using `/v1/chat/completions` with streaming output.
- Request cancellation from the UI.
- Runtime metrics:
  - app-side process state;
  - CPU and memory usage;
  - generated token count and approximate tokens per second from stream timing;
  - optional `/metrics` parsing when `--metrics` is enabled.
- Optional idle sleep support through `--sleep-idle-seconds`.
- Local settings persistence.
- macOS and Windows development builds.

### Excluded From v1

- Full-disk model discovery.
- Built-in model download.
- Multiple simultaneous model processes.
- Router mode and dynamic multi-model loading.
- RAG, embeddings database, document indexing, or vector search.
- Plugin system.
- Cloud sync.
- Account system.
- Automatic llama.cpp updater.
- CUDA/Metal/Vulkan binary matrix management inside the first release.
- Benchmark suite beyond a lightweight launch smoke test.

These exclusions protect the startup experience and keep idle resource use low.

## Performance Principles

- Keep the GUI process separate from inference. `llama-server` can crash or be stopped without taking down the launcher.
- Do not parse model weights. Read GGUF metadata only.
- Cache scan results and invalidate by `path + size + modified_at`.
- Avoid file watchers in v1. Use a clear Refresh action.
- Bound log buffers by line count and file size.
- Avoid frequent UI polling. Use Rust events for process/log updates and low-frequency polling for health/metrics.
- Default to `127.0.0.1` only.
- Use a single active model process in v1.
- Make resource-heavy options explicit: large context, high GPU layer count, `--mlock`, large batch size, and long idle retention.
- Enable `--sleep-idle-seconds` as an optional setting for low-memory users.

## UI Design Direction

The v1 UI should feel like a polished native macOS utility: beautiful, quiet, simple, and practical. It should not look like a marketing page, a web admin dashboard, or an over-decorated AI product shell. The primary visual model is a macOS-style split-view app with a sidebar, title/toolbar area, content list, inspector-style parameter panel, and integrated status/log/chat surface.

### Visual Principles

- Use a calm macOS-inspired light theme as the default.
- Use `-apple-system`, `BlinkMacSystemFont`, and system UI font fallbacks.
- Prefer true white, soft gray surfaces, subtle separators, and restrained blue accent color.
- Keep border radius moderate: 6px to 8px for panels and controls.
- Use shadows sparingly. Prefer separators, tonal surfaces, and spacing.
- Avoid decorative gradients, glowing backgrounds, oversized cards, marketing hero sections, and dense bento layouts.
- Use Lucide icons or equivalent clean line icons for toolbar actions, folder selection, refresh, start, stop, logs, settings, and status. Icons should be small, consistent, and paired with tooltips when meaning is not obvious.
- Use native-feeling controls:
  - segmented controls for mode/profile switches;
  - toggles for boolean settings;
  - steppers or numeric inputs for numeric llama parameters;
  - sliders only when the range is intuitive;
  - disclosure sections for advanced parameters;
  - compact menus for option sets.
- Text should be concise and functional. No visible onboarding essays inside the main app surface.
- Typography should be smaller and denser than a website, but not cramped:
  - 13px to 14px for main UI text;
  - 11px to 12px for metadata, helper text, and log labels;
  - 16px to 20px for section headings.
- UI copy should use clear Chinese labels by default, while technical flags remain in monospace.

### Layout Model

Use a three-region desktop layout:

1. **Sidebar:** model directories, model list filters, recently used models, and refresh controls.
2. **Main configuration area:** selected model summary, preset selector, parameter sections, and command preview.
3. **Runtime area:** process status, logs, metrics, and chat.

The layout should remain ergonomic on laptop screens. The default window should target about `1180x760`, with a minimum usable width near `1000px`. If the width is too narrow, the runtime/chat area can collapse behind tabs, but the selected model and Start/Stop controls must remain reachable.

### macOS-Native Behavior Expectations

- Use the native OS window frame where practical instead of fake browser chrome.
- Keep primary actions in a top toolbar or clearly pinned command row:
  - Select Folder
  - Refresh
  - Start
  - Stop
  - Copy Command
  - Settings
- Keep destructive or resource-heavy actions visually distinct and never hidden inside dense menus.
- Respect keyboard accessibility:
  - `Cmd+,` opens settings on macOS;
  - `Cmd+R` refreshes model list when focus is not in chat;
  - `Cmd+Enter` sends chat message;
  - `Esc` cancels active generation when chat is streaming.
- Preserve focus rings and visible selected states.
- Use platform-aware labels where needed: `Cmd` on macOS and `Ctrl` on Windows.

### Performance-Safe Styling

- Avoid expensive full-window blur effects.
- If translucent sidebar/material styling is used, keep it subtle and provide a solid-color fallback.
- Do not animate large layout regions during model startup or token streaming.
- Use virtualization or bounded rendering for large model lists and log lists.
- Keep animations short, functional, and disabled under `prefers-reduced-motion`.

### Required UI States

The visual design must cover these states before implementation:

- First launch with no model directories.
- Scanning model directory.
- Model list with several GGUF files.
- Selected model with Balanced preset.
- Invalid parameter warning.
- Starting process with streaming logs.
- Healthy runtime with chat enabled.
- Startup failure with actionable error and copy logs action.
- Chat streaming and cancellation.
- Stopped runtime after successful launch.

## Core User Experience

### First Launch

- The app opens to the main launcher screen.
- If no model directory is configured, the model area shows an empty state with a Select Folder action.
- The user picks a directory using a native folder picker.
- The backend scans only that directory and its subdirectories for `.gguf`.
- The model list appears without requiring app restart.

### Normal Launch

- The app loads cached model entries.
- Changed model files are refreshed.
- Missing model files are marked unavailable and hidden by default, with a filter to reveal unavailable entries.
- The user selects a model and a preset.
- The parameter panel updates.
- The command preview shows the final `llama-server` arguments.
- Start validates parameters, port, binary path, and model path before spawning.
- Logs stream into the UI while the health check runs.
- When healthy, the chat panel becomes active.

### Failure Path

- If the model path is missing, show "模型文件不存在".
- If the binary path is missing, show "未找到 llama-server，请选择可执行文件".
- If the port is occupied, show the process-safe message and offer auto-port.
- If `llama-server` exits during startup, show the exit code and last useful log lines.
- If health check times out, keep the process visible and allow Stop, Restart, and Copy Logs.

## Architecture

```text
React UI
  |
  | Tauri invoke/events
  v
Rust backend
  |-- settings service
  |-- model directory scanner
  |-- GGUF metadata reader
  |-- parameter schema and validator
  |-- llama-server command builder
  |-- process manager
  |-- health and metrics client
  |-- system monitor
  |
  v
llama-server process
  |
  v
Local OpenAI-compatible HTTP API
```

The frontend should not call `llama-server` directly for lifecycle-sensitive operations. The Rust backend owns process state, validates paths and parameters, captures logs, and exposes safe Tauri commands/events to the frontend.

## Startup Parameter Coverage

v1 should expose a curated subset of `llama-server` parameters and hide unsupported or highly specialized options behind an Advanced section only when they are safe to validate.

### Basic

- Model path: `-m` / `--model`
- Host: always `127.0.0.1` in v1
- Port: `--port`
- Context size: `-c` / `--ctx-size`
- Predict tokens default: `-n` / `--n-predict`

### Performance

- CPU generation threads: `-t` / `--threads`
- Prompt/batch threads: `-tb` / `--threads-batch`
- GPU layers: `-ngl` / `--n-gpu-layers`
- Batch size: `-b` / `--batch-size`
- Micro-batch size: `-ub` / `--ubatch-size`
- Flash attention: `-fa` / `--flash-attn`
- Memory mapping: `--mmap` / `--no-mmap`
- Memory lock: `--mlock`

### Server and Observability

- Metrics: `--metrics`
- Idle sleep: `--sleep-idle-seconds`
- Log disable is not exposed in v1 because startup diagnostics are important.
- API key is not exposed in v1 because the host is local-only.

### Sampling Defaults

Send these through chat completion request payload instead of process startup when possible:

- `temperature`
- `top_p`
- `top_k`
- `min_p`
- `repeat_penalty`
- `repeat_last_n`
- `seed`
- `max_tokens`
- `stop`

## Command Builder Rules

The Rust backend converts validated parameters to an argument array. It must not build commands by string concatenation.

Example Balanced command:

```text
llama-server
  --model /absolute/path/to/model.gguf
  --host 127.0.0.1
  --port 8080
  --ctx-size 8192
  --threads -1
  --n-gpu-layers auto
  --batch-size 1024
  --ubatch-size 256
  --flash-attn auto
  --mmap
  --metrics
```

Validation rules:

- `model` must be an existing `.gguf` file under a configured directory.
- `port` must be in `1024..65535`.
- `ctxSize` must be positive and should warn above model metadata context when known.
- `threads` accepts `auto` or an integer from `1` to logical CPU count.
- `gpuLayers` accepts `auto`, `all`, or a non-negative integer.
- `batchSize` and `ubatchSize` must be positive.
- `ubatchSize` must be less than or equal to `batchSize`.
- `mlock` should show a warning before enabling because it can pressure memory.
- `host` is not user-editable in v1 and remains `127.0.0.1`.

## Risk Management

### llama.cpp Parameter Drift

Risk: `llama-server` flags change over time.

Mitigation:

- Keep v1 parameter set small.
- Store command builder mapping in one Rust module.
- Add command builder tests.
- Later add `llama-server --help` capability detection before exposing newer options.

### Cross-Platform Binary Distribution

Risk: macOS and Windows binaries differ by CPU/GPU backend.

Mitigation:

- v1 supports user-selected binary in development and packaged sidecar in release.
- First release can ship a conservative CPU/Metal macOS path and a conservative Windows CPU/Vulkan path.
- CUDA-specific packaging is a later release concern.

### Resource Overuse

Risk: large context, aggressive GPU offload, or `mlock` can make low-memory machines unstable.

Mitigation:

- Default Balanced preset is moderate.
- Low Memory preset is prominent.
- Risk warnings appear before launch.
- Idle sleep is available.
- Stop and force stop are always reachable.

### UI Log Flooding

Risk: excessive stdout/stderr updates can make the UI sluggish.

Mitigation:

- Batch log events.
- Bound rendered lines.
- Keep full recent log buffer in backend.
